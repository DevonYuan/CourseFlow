# phase3-03-subtask-core — Sub-task List + Add

## Description

Implement the sub-task list UI in the assignment detail view. This includes rendering existing sub-tasks in order (by `position`), adding new sub-tasks inline with Enter-to-save, deleting sub-tasks with a confirmation dialog, and optimistic UI updates with toast notifications on failure. This is the first interactive sub-task feature and establishes the patterns used by the complete/toggle (Ticket 3.4) and progress indicator (Ticket 3.5) tickets.

**Prerequisite**: Ticket 3.0 (Data Model & IPC Audit) must be complete — the `SubTask` type, `db:subtasks:*` IPC channels, and `window.api.db.subtasks.*` preload bridge must be verified and working.

## Requirements

> Document WHAT is needed and WHY it is needed.

- [ ] **Sub-task list rendering**: In `AssignmentDetailPage`, render a `SubTaskList` component showing all sub-tasks for the current assignment, ordered by `position` (ascending). Each row shows: checkbox (completion state), title, drag handle (placeholder for future reordering), delete button.
- [ ] **Add sub-task inline**: Provide an "Add sub-task" input at the bottom of the list (or inline at the end). Pressing **Enter** saves the new sub-task via `db:subtasks:upsert`. Input clears on success. Focus returns to input for rapid entry of multiple sub-tasks.
- [ ] **Delete sub-task with confirmation**: Each sub-task row has a delete icon/button. Clicking opens a confirmation dialog (native `confirm()` or a small modal). On confirm, call `db:subtasks:delete(id)`. On cancel, do nothing.
- [ ] **Optimistic UI**: All mutations (add, delete) update the local Zustand store **immediately** before the IPC call resolves. If the IPC fails, roll back the optimistic update and show an error toast.
- [ ] **Loading state**: Show skeleton placeholders while sub-tasks are loading (via `db:subtasks:list`).
- [ ] **Empty state**: When an assignment has no sub-tasks, show a friendly empty message ("No sub-tasks yet — add one below") and the add input.
- [ ] **Keyboard accessibility**: 
  - Tab navigates through sub-task rows (checkbox, title, delete button)
  - Enter/Space on checkbox toggles completion (delegates to Ticket 3.4's toggle IPC)
  - Enter in add input saves
  - Escape closes delete confirmation / clears add input
  - Focus management: after delete, focus moves to next row or add input
- [ ] **Live updates**: Subscribe to `window.api.onDbChanged` for `sub_tasks` table changes. If another window/process adds/deletes a sub-task, the list updates automatically.
- [ ] **Persist position**: New sub-tasks get `position = max(existing positions) + 1` (append to end). The `position` field is set by the frontend (not auto-generated by backend) to keep ordering deterministic.

## Designs & Constraints

> Any non-obvious designs or constraints to the design that MUST be followed.

- [ ] **Component structure**: Create `SubTaskList` (container), `SubTaskRow` (individual row), `SubTaskAddInput` (add form) as separate components in `src/frontend/src/components/subtasks/`.
- [ ] **Zustand store**: Extend the existing assignment/detail store (or create a `useSubTaskStore`) with `subTasks: SubTask[]`, `addSubTask(title)`, `deleteSubTask(id)`, `setSubTasks(list)`, `optimisticAdd(tempId, title)`, `rollbackAdd(tempId)`. Keep it simple — sub-tasks are scoped to one assignment, so a map `assignmentId -> SubTask[]` works well.
- [ ] **Temp IDs for optimistic adds**: Generate a client-side UUID (e.g., `crypto.randomUUID()`) as a temporary `id` for the optimistic sub-task. When the IPC succeeds, replace the temp ID with the real ID from the response. This avoids flicker and enables rollback.
- [ ] **Delete confirmation**: Use a small accessible modal (not native `confirm()`) for consistency with the app's toast/dialog system (established in Phase 1 Ticket 1.15). The modal should have: title "Delete sub-task?", message "This cannot be undone.", "Cancel" (focused by default), "Delete" (destructive style).
- [ ] **Toast on failure**: Use the existing toast system (Phase 1) for error messages: "Failed to add sub-task", "Failed to delete sub-task". Include a "Retry" action on the toast for add failures (re-sends the IPC).
- [ ] **No drag-reorder yet**: Ticket 3.3 only renders a drag handle (grip icon) as a placeholder. Actual drag-and-drop reordering is out of scope for Phase 3 (can be added later if trivial).
- [ ] **Sanitization**: Sub-task titles are plain text — no HTML/markdown. Trim whitespace; reject empty titles (show inline error or disable save).
- [ ] **Max length**: Enforce a reasonable max length (e.g., 200 chars) on sub-task titles, matching the DB column constraint.
- [ ] **Completion checkbox**: Render a checkbox that reflects `completed` state. Clicking it calls the toggle flow (Ticket 3.4) — for this ticket, the checkbox can be read-only or wire a placeholder `onChange` that calls a stub. **Do not implement toggle logic here** — that's Ticket 3.4.
- [ ] **Responsive**: Works at 800px minimum width. Sub-task rows stack cleanly; add input spans full width.

## Acceptance Criteria

> Document the criteria that must be met for the ticket to be considered complete.
> Each criteria will be written as an automated test (e.g., Playwright) if possible.

- [ ] **List renders**: Opening an assignment detail view loads and displays all sub-tasks in `position` order.
- [ ] **Add works**: Typing a title in the add input and pressing Enter creates a sub-task via IPC; it appears immediately in the list (optimistic); the input clears and retains focus.
- [ ] **Add validation**: Empty title (or whitespace only) does not submit; shows inline error or prevents submit. Title > 200 chars is truncated or rejected.
- [ ] **Delete works**: Clicking delete on a row opens confirmation modal; confirming calls IPC and removes the row immediately (optimistic); canceling leaves the row.
- [ ] **Optimistic rollback**: If `db:subtasks:upsert` or `delete` returns an error (`ok: false`), the optimistic update is rolled back and an error toast appears with "Retry" (for add).
- [ ] **Loading state**: Skeleton rows show while `db:subtasks:list` is pending.
- [ ] **Empty state**: Assignments with no sub-tasks show the empty message and add input.
- [ ] **Live updates**: Adding/deleting a sub-task in another window (or via direct DB manipulation) triggers `db:changed` and the list updates without refresh.
- [ ] **Keyboard navigation**: 
  - Tab moves through checkbox → title → delete button → next row → add input
  - Enter in add input saves
  - Escape in add input clears it
  - Escape in delete modal closes it
  - After delete, focus moves logically (next row or add input)
- [ ] **Screen reader**: Rows have proper ARIA (checkbox role, `aria-checked`, delete button `aria-label="Delete sub-task: {title}"`). Add input has `aria-label="Add sub-task"`.
- [ ] **Position persisted**: New sub-tasks receive `position = max + 1`; the backend stores it; reloading the page preserves order.
- [ ] **TypeScript compiles**: `pnpm typecheck` passes.
- [ ] **Lint passes**: `pnpm lint` passes.

## Notes

> Any additional context, risks, or considerations.

- **Dependency on Ticket 3.0**: This ticket cannot start until the audit confirms `SubTask` type has `position`, `created_at`, `updated_at`; `db:subtasks:list/upsert/delete` IPC channels exist and return correct `IpcResult<SubTask[]>` / `IpcResult<SubTask>` / `IpcResult<void>`; preload exposes `window.api.db.subtasks.list/upsert/delete`.
- **Dependency on Ticket 3.1/3.2**: Needs the detail route (`/assignments/:id`) and data loading hook (`useAssignmentDetail`) to get the `assignmentId`. Can develop in parallel with a mock assignment ID.
- **Zustand pattern**: Follow the existing store pattern from Phase 1/2 (e.g., `useAssignmentStore`, `useFilterStore`). Keep sub-task store simple — scoped to one assignment at a time.
- **Temp ID strategy**: Use `crypto.randomUUID()` for optimistic IDs. The backend returns the real UUID on upsert. Map `tempId -> realId` in the store.
- **Delete modal**: Reuse the modal/dialog pattern from Phase 1 (Ticket 1.15 error boundary/toast system). If no reusable modal exists yet, create a simple one here and extract to shared later.
- **Testing**: 
  - Unit: `useSubTasks` hook (mock IPC), `subtaskStore` actions.
  - Component: `SubTaskList`, `SubTaskRow`, `SubTaskAddInput`, `DeleteConfirmModal` (React Testing Library).
  - E2E: Playwright test in `src/frontend/test/subtasks.spec.ts` — add, delete, validation, empty state, keyboard.
- **Future-proofing**: The `position` field and drag handle placeholder make drag-reorder (future) straightforward — just need to implement `onDragEnd` that calls `db:priority:reorder` equivalent for sub-tasks (new IPC channel `db:subtasks:reorder` would be needed).
